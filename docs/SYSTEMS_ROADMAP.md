## 1. ANE-LatticeZK: Lattice-Based zk-SNARK with RNS-Matrix Linear Algebra

**Status**: 🟢 Complete (ANE RNS-MatVec infrastructure, full prove/verify/sign)
**TRL**: 5/10

### What We Have
- ANE RNS-MatVec infrastructure (`core/orion_latticezk.m`, `core/orion_rns.m`)
- RNS configuration for Dilithium-3: 5 moduli {97, 101, 103, 107, 109} (~33.5 bits > q)
- Per-residue ANE evaluation via conv1x1 batching (~0.45ms/iter)
- CRT reconstruction pipeline verified with test (A=1, s=1 → [4,4,4,4] ✓)
- High-level `latticezk_matvec(A, s, k, l, q, result)` API
- Fiat-Shamir transcript (`LatticeZKTranscript`) with challenge generation
- Prove/Verify infrastructure (`latticezk_prove`, `latticezk_verify`)
- Proof serialization (`latticezk_proof_serialize`, `latticezk_proof_deserialize`)
- Signing (`latticezk_sign`, `latticezk_verify_sig`) with keygen
- Test suite (`tests/test_latticezk.m`) - 36 tests passing

### Known Simplifications (Not Bugs)
- `expand_a`: XOR-based pseudo-random (not SHAKE128) — for testing/prototyping
- `sample_short_vector`: Deterministic pattern (not CBD) — for reproducibility
- `sign`: No rejection sampling loop — simplified protocol
- Matrix elements are scalars, not polynomials — ANE handles first-coefficient only

### Core Flow
```
Witness s (short vector)
    ↓
RNS Decomposition (q → q₁, q₂, ..., qₖ)
    ↓
For each residue qᵢ:
    A*s mod qᵢ → ANE MatVec (batched 1×1 conv)
    ↓
CRT Reconstruction → A*s mod q
    ↓
Fiat-Shamir → Challenge
    ↓
Sign with noise → Signature
```

### References
- Lyubashevsky-style lattice proofs
- Greyhound (transparent SNARKs)
- Dilithium signature scheme

### Conv-PCS ANE Status
The ANE path is now fully operational. Root cause of "InvalidMILProgram" was a subtle MIL syntax issue: the function signature `func main<ios18>(tensor<fp32, [1, 8, 1, 16]>)` was missing the input variable name `x`. The working form is `func main<ios18>(tensor<fp32, [1, 8, 1, 16]> x)`. This is auto-generated by `orion_mil_program()` when the input array contains a proper variable declaration like `tensor<fp32, [1, 8, 1, 16]> x` instead of just `tensor<fp32, [1, 8, 1, 16]>`.

### Core Flow
```
Polynomial P(x₁,...,xₙ) as tensor
    ↓
Commit: convolve with random kernel K → C
    ↓
Open: batched 1×1 conv + reduction
    ↓
Verify: check C = eval(P, point) + Merkle proof
```

## Technical Notes

### ANE Constraints
- dim ≤ 1024: Full efficiency
- dim 1024-2048: Works, slower
- dim > 4096: NOT feasible (32MB SRAM limit)
- seq ≥ 16: Required minimum
- fp16 safe range: moduli < 128

### RNS Strategy
For Dilithium-3 q = 8383489 (~23 bits):
- Need ~2-3 small moduli (e.g., 97, 101, 103 gives ~47 bits > 23 bits)
- Or ~5 tiny moduli (3×5×7×11×13 = 15015 < q, but we want > q)
- Use: {97, 101, 103, 107, 109} → ~47 bits (covers 23-bit modulus with headroom)

### Weight Patching
- Compile limit: ~119 per process
- Weight patch: ~6ms (vs 2-12ms full compile)
- Use donor program + patched weights to preserve budget
